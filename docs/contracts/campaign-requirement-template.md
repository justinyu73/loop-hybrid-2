# Campaign 需求範本

狀態：active。這是一份給目標專案用的範本：複製到你的專案、填掉所有 `<…>`，就成為一份已核准的有界路線圖。之後 loop 照它一階一階執行。人先定好 Goal 與 envelope，之後只在越界、真正的岔路、證據不足、重複失敗或階段性收尾時出手，不需要逐個節點確認。

對應的 contract 欄位見 `project_runtime_contract.example.json`。每一階對應 `campaign.stages[]` 中的一個 stage。

## 鎖死約束（每一條都要標作用域）

| 約束 | 作用域 |
|---|---|
| <例：不連網、無遙測> | 產品 runtime（不含開發與建置工具鏈） |
| <例：不改既有產品行為> | 產品行為 |
| 外部作用（push、merge、發布）只經注入的 port，並受 effect guard 約束；發布、release 與產品終驗留到收尾 | 流程 |
| 不繞過：不跳過或弱化測試、不吞錯、不用隱藏的 fallback 假裝成功 | 全域 |

> 約束沒有標作用域（例如只寫「全離線」），loop 會把開發期的動作誤判為違規而停下。

## 階段路線圖

每一階都是一個受限的 work unit。**確定性階段**必須附一支 committed、任何人在任何 shell 重跑都同樣綠的驗收燈；**人工階段**由人判斷，loop 只負責建出來。

| 階段 | 目標與最小功能 | 最小可驗收結果 | 驗收型態 | 驗收燈 | 不能做的事 | 進入下一階段的條件 |
|---|---|---|---|---|---|---|
| <D1> | <…> | <可確認的具體結果> | 確定性／人工 | `<checks/…>` | <…> | 驗收燈綠 |
| <D2> | <…> | <…> | 確定性／人工 | `<checks/…>` | <…> | <…> |

驗收燈的五條規則（寫錯等於沒有驗收）：
1. 在 base 上必須是紅的。
2. 決定性、與環境無關。
3. 綠燈必須是「工作完成才成立」的正向證據。
4. 驗證器自身出錯時必須非零退出。
5. 驗證器必須在 `allowed_paths` 之外。

> 型態標記是關鍵：確定性的階段由 loop 自跑；人工的階段（語意、策展、設計品質）由 loop 建出來，停下來給人判斷。不要替人工階段掛一盞測不到真正品質的燈。

## 執行與停止契約

- **自動流程**：確定性階段 → 實作 → 驗收燈 → 綠就自動接下一階。已核准的 envelope 內，不逐步等人。
- **必須停下問人**：真正的範圍或設計岔路、驗收無法寫成腳本、紅到修不動，或需要碰憑證、外部發布。
- **禁止**：envelope 外的作用、擅自擴張範圍、繞過測試，以及用機器綠燈冒充最終的人工驗收。

## Goal 收尾驗收（人，階段性）

全部階段綠，且下方的最終機器驗收在乾淨 shell 重跑全綠之後，由人對產品目標做收尾驗收。發布與 release 由目標專案的政策決定。

## 最終機器驗收

從一個乾淨的 shell 逐一重跑，全部 exit 0 才算數：

```sh
sh checks/<…>.sh
python3 -B -m unittest discover -s tests
```

## 與現行程式的差異

- 原範本把底層概念指向外部知識庫筆記，並允許在特定 envelope 內由合併 gate 直接合併。公開版不引用外部知識庫；外部作用只經注入的 port 與 effect guard。
- 原範本建議把 value commit 與 done commit 分成兩顆。公開版的 loop 在一次性 clone 中只產出一個候選，由驗收燈與 delivery 綁定判定，沒有固定的雙 commit 慣例。
